# SEOレビュー：初版

`/seo` は TSサイトのページ台帳と Search Console CSVを使い、次に確認するページを選ぶ画面です。成果指標は将来的に新規の有効問い合わせ企業数へ接続します。初版は検索データの比較までで、問い合わせや受注との因果関係は推定しません。

## 使い方

1. `npm ci`、`npm run dev` で起動し、トップの「検索データから改善を考える」を開く。
2. 「架空データで試す」で動作を確認できる。デモを終了してから実データを取り込む。
3. ページ台帳の名称、目的、依頼につながる重要度、最終更新日を整える。初期26件は公開URLの確認候補。タイトルのクロール、インデックス確認、完全性の保証は行わない。
4. Search Consoleの検索パフォーマンスで「ページ」タブを選び、クリック数・表示回数・CTR・掲載順位を有効にする。TS配下にページを絞り込む。
5. 同一の検索タイプ・国・デバイス・その他フィルタで、同日数の重ならない2期間を別々にエクスポートする。比較モードのCSV、日付別CSV、クエリCSVは対象外。ZIPは展開してページCSVだけを選ぶ。
6. 画面に各期間、CSV、検索条件を入力する。期間はCSVに含まれないため、Search Consoleで指定した日付をそのまま記入する。確定済みデータを使う。
7. 最大5件の候補を確認し、今週実行する1〜2件を判断する。必要なクエリ調査、実験、写真の準備はこの時点では手作業。
8. バックアップJSONを保存する。同じ画面から復元できる。

## 保存と情報の範囲

- ブラウザのlocalStorage `sitebot.seo.v1`。CSV・台帳をサーバーや生成APIに送信しない。共有PCでは同じブラウザの利用者が閲覧できる。
- 保存は入力検証の成功後。CSV解析・期間検証・容量エラー時は現在のワークスペースを置き換えない。
- 1組の比較期間のみ保持する。次の取り込み前にバックアップする。アカウント共有・複数端末同期・時系列履歴は未実装。
- 壊れた保存データは読み込み時に自動上書きしない。復元または初期化をユーザーが選ぶ。
- 実顧客名、機密情報、案件原文を台帳に入れない。検索CSVとバックアップも公開Gitには入れない。
- デモは架空と明示し、実CSV取込を無効化する。デモへの切り替えは確認付きで台帳を置換する。既存データは先にバックアップする。

## データ契約

`src/seo/model.ts` の version 2。旧version 1の保存データ・バックアップは読み込み時に移行し、作業一覧を空で追加する。新しいバックアップは旧アプリでは読み込めない。`pages` と `comparison` を別々に管理し、CSVで初めて見つかったURLは未設定の重要度で台帳に追加する。

- 英語/日本語のページ別CSVを受け付ける。URL、クリック数、表示回数、順位を必須とする。CTR列は任意で、値はクリック数÷表示回数から計算する。
- BOM、CRLF、引用符、引用符で囲まれた桁区切りを処理する。2MB・10,000行まで。
- 不正な数値、空欄の件数、負数、クリック数>表示回数、重複URL、対象外ドメイン・パスは拒否する。
- URLの末尾スラッシュ、クエリ文字列は推測で統合しない。フラグメント付きURLは拒否。
- 表示回数ゼロのCTRと順位は不明として表示する。片期間に行がなければゼロ補完しない。
- ページ合計をサイト全体の指標として表示しない。平均順位の単純平均や、クエリCSVとページCSVの推測結合はしない。
- CSVの期間・検索条件は自動検証できないため、ユーザーの確認を記録する。Googleのエクスポート上限や省略により、比較対象が全件とは限らない。

## 候補抽出（調整可能な初期ルール）

1. 両期間の行がなければデータ不足。
2. 更新日から今回の集計終了日まで28日未満なら経過観察。集計後の更新も含む。誤記・機能不具合は待たずに修正する。
3. いずれかの期間が100表示未満ならデータ不足。低需要のB2Bテーマを切り捨てる判定ではない。期間を延ばすか商談情報とあわせて判断する。
4. 重要度0（集客対象外）は改善候補に含めない。
5. クリック減少＋平均順位2以上悪化、クリック減少＋平均順位差1以内＋CTR1ポイント以上低下、平均順位4〜15を候補とする。
6. 優先度は人間が設定する重要度×3＋理由の点数（上の順に3・2・1）。重要度不明は暫定扱いで既知の候補の後に表示。最大5件。

これは社内の確認順を決めるヒューリスティックであり、Googleの採点、特定クエリの順位、書き換えによる改善予測ではない。CTR低下の原因をAI回答と断定しない。

## 既存ハーネスへの接続方針

- この段階で `content/pages.json`、`sitebot.yaml`、技術確認・承認ストアは書き換えない。SEO台帳は編集指示や公開許可ではない。
- 次段階：候補を永続タスクへ変換し、調査根拠、実験条件、写真、必要な技術確認を紐づける。
- その後：構造化された既存ページとレシピの対応を確認し、既存のApplication/ハーネスを通して下書き生成。TSXをそのまま自動変更しない。
- 公開前：認証・権限・永続ストア、技術確認UI、対象リポジトリ、PR作成、プレビュー・差分確認、変更コミットへの承認を接続する。
- 最後：GSC APIの読み取りと定期実行、公開後の履歴比較、匿名化された問い合わせ指標へ接続する。

`test/seo.test.ts` はCSVの引用符/桁区切り/重複/不正値、スコープ、期間、欠損、ゼロ、低サンプル、更新後の経過観察、候補の根拠・順序、バックアップスキーマを検証する。

## 改善作業と制作指示

- 候補から「今週の作業に追加」。週は日本時間の月曜開始。同じ週に選べるのは2件（見送りを除く）で、同じURLの未完了作業は重複させない。
- URL・管理名・選定時の前後期間・検索条件・クリック/表示回数/平均順位・判断理由を作業に保存する。CSVの入れ替えや台帳編集では過去の選定根拠を更新しない。
- 目的、対象クエリと確認元、調査、追加実験、写真、根拠資料、適用範囲を記入する。公開用の根拠は自社検証に基づくものを用意する。顧客の機密情報は入力しない。
- 「今週の作業 → 調査中 → 検証・写真待ち → 下書き準備完了 → 対応完了」、または「見送り」。状態は人間が選ぶ。
- 下書き準備完了と対応完了には、目的・クエリと確認元・調査・根拠・適用範囲の記入と資料準備のチェックが必要。
- 準備完了後にMarkdownの制作指示を出力できる。実験条件や画像をAIが補完しない。これは資料の準備状況であり、技術的な承認ではない。
- 制作指示を既存の開発環境で使う場合も、構造化されたコンテンツとレシピの対応を確認してハーネスを通す。現在は画面から生成API・PR・公開へ自動送信しない。
- 作業とメモもブラウザ内保存・バックアップの対象。デモ作業と実データは混在できない。バックアップに記録された準備状態は認証された承認記録ではない。


## SEOメタデータの下書き作成

実作業の実績ページが「下書き準備完了」になると「下書き作成に進む」が表示される。既存ハーネスの `PublicAchievementSchema` に合う公開用JSONを選択する。JSONのslugと作業URLが異なる場合は受け付けない。現状のTSXやHTMLをこの入口から直接編集することはできない。

タイトル・H1・説明文の修正案と、画面に表示された作成指示を確認して送信する。標準では入力した案をそのままハーネスへ渡す。「外部AI」を明示的に選んだ場合だけ、既存の `SITEBOT_PROVIDER=http` / `SITEBOT_GENERATION_URL` / `SITEBOT_GENERATION_API_KEY` 設定を用いて `{payload: TextEditPayload}` を送信する。APIはタイトル・H1・説明文だけのJSONパッチを返す必要があり、本文・画像・facts・承認フィールドなどを含む結果は拒否する。生成API未設定の場合は手入力方式を使用する。

- この操作では対象の公開用JSON・明示した指示・修正案をアプリのサーバーに送る。検索CSVと作業メモ全体は送信しない。公開用情報で自社検証に基づき機密情報を含まないことを操作前に確認する。
- AIへは現在の `generated` 文章と指示だけを渡す。事実データや画像バイナリは渡さない。生成文章に含まれるキャプションなどの文字列は送信対象に含まれる。
- 元データと指示の機密語を送信前に検査し、出力も既存ハーネスで検査する。禁止語検査は人間の守秘確認を代替しない。
- `runTextEdit` を通し、写真ID・事実データ・表・工程・本文・関連リンクは変更できない。変更前後の文章と保持した項目数を表示する。
- 元JSONをアップロードしただけでは以前の技術確認は成立しないため、元データと修正案の確認を常にpendingで追加する。自動承認しない。
- 下書きは `data/sitebot/seo-drafts/<jobId>/` の中にのみ保存する。元データ `source.json`、結果 `summary.json`、ハーネスのコンテンツJSONとジョブを保存する。失敗・変更なしの場合は作業ディレクトリを除去する。
- 修正案JSONを画面からダウンロードできる。これは公開承認を含まない下書きで、既存の確認フローへ渡すためのファイル。画面上の結果表示はリロードすると消え、サーバーのファイルは残る。
- 本番サイトの全構造化データとの同期、認証された技術確認・公開承認、PR作成と本番反映は未接続。現段階は内部の開発・検証環境で使用する。

## 保存した下書きの再確認

1. SEO画面の「保存したSEO下書きを開く」から一覧へ移動し、対象の修正案を開く。ブラウザの台帳バックアップとは別に、サーバーの `SITEBOT_DATA_ROOT/seo-drafts` に残る。
2. 対象の公開ページ、タイトル・H1・説明文の差分、技術確認項目を照合する。元JSON・本文・写真・数値の整合性を確認する。
3. 依頼者と別の技術確認担当者が、項目ごとに「根拠を確認済み」または「要修正」と理由を記録する。要修正は確認待ちに戻り、過去の理由も履歴に残る。本文の変更はこの画面では行わず、修正する場合は新たな下書きを作る。
4. 技術確認がすべて終わっても、状態は「内容の確認」。ダウンロードJSONも `draft` のままで、確認履歴は公開承認やGitコミットへの承認にならない。

開発環境で技術確認を試す場合は、サーバーに `SITEBOT_DEV_USER_ROLE=technical-reviewer` と依頼者と異なる `SITEBOT_DEV_USER_ID`、担当者の `SITEBOT_DEV_USER_NAME` を設定して再起動する。同じ `SITEBOT_DATA_ROOT` を指定する。ブラウザから担当者ID・権限を指定することはできない。これは開発用の利用者注入であり、本人認証・本番の権限管理ではない。

確認記録は下書きと元JSON・作業記録のハッシュに結び付く。保存後に内容が変わっていたら過去の確認を引き継がず、読込を止める。別画面で確認が更新された場合も古い版からの記録を拒否するため、再読み込みして差分を確認する。読めない下書きは一覧に件数を表示し、他の正常な下書きは開ける。

保存は単一Node.jsサーバーのファイルストアを前提とし、確認履歴ファイルを一時ファイルから置き換える。複数サーバー・プロセスでの同時書込には未対応で、導入時にトランザクション付き永続ストアへ移行する。下書きと確認メモはサーバーのバックアップ対象に含める。顧客名や機密情報はメモにも書かない。

## 公開ページの取り込みと元JSONの照合

1. `/seo/sources` または実績ページの下書き入力欄で「公開ページを取得」を押す。対象は `https://www.macsystems.co.jp/ts/` 配下の末尾スラッシュ付きURL。クエリ・フラグメント・別ホスト・リダイレクトは受け付けない。
2. 取得時点のHTMLと取得日時を `SITEBOT_DATA_ROOT/seo-sources` に保存する。画面にはHTMLから読み取ったタイトル・H1・説明文・canonical・robots・見出し・画像一覧・表と埋込の件数を表示する。必要なら元HTMLをダウンロードする。
3. 下書き画面で実績JSONをアップロードしている場合は、公開ページのタイトル・H1・説明文と照合する。空白の違いだけを整えて比較し、会社名の付加や別の文言を勝手に同一視しない。相違は現状確認のための表示で、JSONや公開ページの自動書換えには使わない。
4. 本文・工程・写真・数値・条件の整合性は別途確認する。HTMLから実験の根拠、公開可否、過去の技術確認を復元しない。実績JSONは従来どおり必要で、取り込んだHTMLは制作の原本JSONの代用にならない。

取得は15秒・2MBまでのUTF-8 HTMLを対象とし、固定のTSホストだけにアクセスする。サーバー側でJavaScriptを実行せず、画像・動画などの外部リソースを取得せず、HTMLをAIへ自動送信しない。画面表示後のDOM、CSSによる可視性、HTTPのrobots指定、検索順位、インデックス状況は判定しない。動画がHTMLに無くクリック後に追加される場合、埋込件数は0でも動画がないとは限らない。

保存HTMLは取得時点の記録で、最新の状態を保証しない。ハッシュが一致しない保存ファイルは読込を拒否する。再取得するたびに別の記録を残し、過去のHTMLを上書きしない。サーバーの永続化・バックアップ対象に `seo-sources` も含める。本番リポジトリのTSX/JSONデータとの同期は未接続。

## 下書きの公開原本と変更確認

1. 新しい実績下書きでは、対象URLの公開HTMLを取得してから作成する。サーバーは取得記録のIDを読み直し、URL一致と取得から30分以内であることを確認する。ブラウザからHTML・ハッシュを原本として直接指定することはできない。
2. 取得したHTMLと識別情報を下書きの `origin.json` にコピーする。作成後の原本差し替えは行わない。共有の取り込み履歴を消しても下書き内の原本は残る。
3. 下書き確認画面で「公開ページを再取得して確認」を押す。原本に記録された固定URLだけを取得し、HTML全体のSHA-256を比較する。一致した確認から30分以内だけ技術確認を記録でき、記録時にもサーバーで期限を検査する。30分は本アプリの運用上の期限であり、Googleの要件ではない。
4. HTMLが変わっていた場合、過去の技術確認を現在の承認として使わず、全項目を確認待ちとして表示する。過去の理由・担当者・日時は履歴に残す。一度変更を検知した下書きは、公開ページが元に戻っても確認可能に戻さない。現状と元JSONを照合し、新たに公開HTMLを取得して下書きを作り直す。
5. 取得失敗や期限切れの場合も記録を止める。変更が検知されていない下書きは、一致するHTMLを再取得すれば確認を再開できる。原本未紐付けの旧下書きは、閲覧・JSON保存だけを継続し、新しい下書きで原本を紐付ける。

確認履歴には原本HTMLのハッシュと再取得時刻も記録する。再取得中に技術確認が記録された場合は、その履歴を消さずに原本確認を反映する。別の原本確認が先に終わった場合は、古い一致結果で上書きしない。変更の検知は保持する。

HTML内の日時・埋込用ID・共通ヘッダーの変化も変更として扱う。本文だけの意味比較ではなく、安全側の一致確認である。画像ファイルが同じURLのまま差し替わった場合やJavaScript実行後の表示の変更は検知しない。この再取得は手動で、常時監視ではない。記録直後の変更も防げないため、今後の公開処理では直前の確認と対象リポジトリのコミットへの承認を別途接続する。

### 技術確認後の本番側への引き渡し

下書き詳細の「確認済みの引き渡しデータを保存」から、依頼者がJSONを保存する。
全確認項目が確認済みで、公開HTMLが原本と一致した確認から30分以内の場合のみ書き出せる。
書き出し時にもサーバーで状態・利用者・画面のリビジョンを検証する。
原本JSON、title/H1/descriptionだけの修正案、原本と修正案のハッシュ、公開HTMLのハッシュ、各項目の最新の確認根拠を含む。
下書きの管理用metaを本番JSONへコピーせず、元JSONへのメタデータ変更だけを提案する。

本番リポジトリが `content/achievements/<slug>.json` のPublicAchievement形式を使う場合、以下で読み取り専用の照合を行う。

```sh
node --import tsx src/cli.ts verify-seo-handoff --file /path/bga-seo-handoff.json --root /path/production-repo
```

対象パス・修正範囲・ハッシュ・確認記録を検証し、本番側のJSONが元データと違う場合やリポジトリ外へのシンボリックリンクの場合は停止する。成功してもファイルは変更しない。

このパッケージは署名された承認書ではない。開発用の利用者設定と確認メモは認証済みの身元保証にはならない。
CLIは公開HTMLを再取得せず、現在の技術確認状態をサーバーへ問い合わせない。保存後の確認取り消しや公開ページの変更を追跡するものではない。
適用前に最新の確認状態と公開原本を照合し、差分をレビューする。既存の対象コミットSHAに対する依頼者・公開担当者の承認は別途必要。
実際のTS本番ソースがTSXや別形式の場合、このCLIだけでは接続できない。ソース構成を確認した上で変換処理を作成する。
