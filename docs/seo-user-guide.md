# SEO改善アプリ 利用ガイド

対象：ページの改善を依頼する人、技術内容を確認する人、運用担当者  
更新日：2026年10月11日  
対応版：PR #10・#11の機能を含む版

このアプリでは、検索データから改善するページを選び、根拠を整理して、修正案を技術担当者に確認してもらえます。目的は、受託分析・試験の相談につながるページを育てることです。

**まずは「架空データで試す」から始めてください。実際のサイトへの反映は、現在は運用担当者への引き渡しまでです。**

## 1. 最初に知っておくこと

| やりたいこと | 現在できること |
| --- | --- |
| どのページから改善するか決める | Search ConsoleのCSVを2期間で比較し、候補を確認する |
| 調査・実験・写真の準備を管理する | 今週の作業を選び、準備内容を記録する |
| 制作を依頼する | 準備した内容をMarkdownの制作指示として保存する |
| 既存ページの文章を直す | 対応形式の実績JSONから、タイトル・H1・説明文の修正案を作る |
| 技術内容を確認する | 依頼者とは別の担当者が、根拠と確認結果を記録する |
| 本番担当者へ渡す | 確認済みの修正案・元データ・確認根拠を一つのJSONに保存する |
| サイトを公開する | アプリからの自動公開は未接続。運用担当者が別途対応する |

タイトルは検索結果などに使うページ名、H1はページ内の主見出し、説明文は検索結果向けの紹介文です。検索結果の表示内容が、そのまま採用されるとは限りません。

このガイドは「検索データから改善を考える」の使い方を扱います。トップ画面の「実績を追加する」は別の新規制作機能です。

## 2. 誰が何をするか

| 担当 | 作業 |
| --- | --- |
| 依頼者 | 改善候補を選ぶ、調査・資料を用意する、修正案を作る、確認後のデータを保存する |
| 技術確認担当者 | 自社検証の記録と文章を照合し、各項目の判断と根拠を記録する |
| 運用担当者 | アプリの起動、担当者設定、元JSONの用意、バックアップ、本番への反映を担当する |

依頼者は自分の下書きの技術確認を記録できません。技術確認が終わっても、公開の判断は別途必要です。

現在は開発・検証用のアプリです。通常のログイン画面はなく、利用者と役割の設定は運用担当者が行います。利用者は運用担当者から案内されたURLを開いてください。

## 3. 最初の練習

1. トップ画面で「検索データから改善を考える」を開きます。
2. 既存データがある場合は、先に「バックアップを保存」を押します。
3. 「架空データで試す」を押します。デモへの切り替えは現在の台帳を置き換えます。
4. 改善候補を読み、1件を「今週の作業に追加」します。
5. 「調査・準備を記入」を開き、項目と作業状態を確認します。
6. 練習が終わったら「デモを終了する」を押します。元のデータを戻す場合は、保存したバックアップを復元します。

デモで試せるのは、候補選びや準備内容の記入などです。実ページの下書き作成は実データの作業で行います。比較データが既にあると、デモ開始ボタンが使えない場合があります。デモのために実データを消す必要はありません。

## 4. 検索データを取り込む

### 用意するもの

- 前期間と今回の期間、それぞれの「ページ別CSV」
- それぞれの開始日・終了日
- 検索条件のメモ

CSVはSearch Consoleから用意します。運用担当者に依頼するときは、次のように伝えてください。

> TS配下を対象に、同じ検索条件で、日数が同じ・重ならない2期間のページ別CSVをください。クリック数・表示回数・掲載順位を含め、指定した日付と検索条件も教えてください。

たとえば「2026年8月1日〜28日」と「2026年8月29日〜9月25日」は、重ならない28日間です。これは入力例なので、実際に出力したCSVの期間に置き換えます。

### 画面での操作

1. 「1. 検索データを取り込む」で、前期間の日付とCSVを選びます。
2. 今回の期間の日付とCSVを選びます。
3. 「検索条件のメモ」を入力します。例：`ウェブ / 国・デバイス指定なし / ページURLはTS配下`。
4. 両期間の検索条件と確定データを確認し、チェックを付けます。
5. 「取り込んで比較する」を押します。

ZIPは展開して、ページ別のCSVを選びます。クエリ別・日付別・比較モードのCSVは使えません。日付はファイルから自動判定できないため、正確に入力してください。

## 5. 改善するページを選ぶ

先に「4. ページ台帳」で、管理名・目的・重要度・最終更新日を整えます。更新日が不明なら空欄で構いません。台帳の編集だけで公開サイトの文章が変わることはありません。

重要度は次を目安に設定します。

| 重要度 | 判断の目安 |
| --- | --- |
| 3 | 依頼・見積相談に直結する |
| 2 | 依頼先の比較検討を支える |
| 1 | 技術理解を支える |
| 0 | 現在は集客対象にしない |

「2. 改善候補を確認する」で理由を読み、進めるページの「今週の作業に追加」を押します。選べるのは日本時間の月曜始まりで週2件までです。同じページの未完了作業は重複して追加できません。

**候補に出た理由だけで書き換えないでください。** ページ全体の平均順位から、特定の検索語の順位は分かりません。対象URLの検索語と実際のページを確認してから、変える箇所を決めます。「データ不足」は不要なページという意味ではありません。

## 6. 調査・実験・写真を準備する

「3. 選んだ作業を進める」から「調査・準備を記入」を開きます。

| 入力欄 | 書く内容の例・目安 |
| --- | --- |
| この改善で増やしたい相談 | 材料や試料のどの困りごとについて相談してほしいか |
| 確認した対象クエリ | 実際にデータで確認した検索語 |
| クエリの確認元・確認日 | 対象URL、調査期間、確認日 |
| 調査結果・変更したい箇所 | 現在不足している説明と、必ず残す写真・表・注意書き |
| 追加の自社検証計画 | 試料・条件・比較方法。不要ならその理由 |
| 写真・図の準備 | 写真の参照先、スケール、撮影条件。不要ならその理由 |
| 主張の根拠・資料の参照先 | 自社検証の記録ID、観察結果、写真IDなど |
| 適用範囲・限界 | 今回の条件で言えること、未確認のこと |

ここには、顧客名・案件原文・顧客の写真・機密情報を入力しません。公開用の説明は自社検証に基づいて用意します。入力例の数値や他ページの結果を、自分の実験結果として流用しないでください。

作業状態は進み具合に合わせて選び、「作業を保存」を押します。

`今週の作業 → 調査中 → 検証・写真待ち → 下書き準備完了 → 対応完了`

途中で進めないと決めた場合は「見送り」にできます。準備が整ったら必要項目を埋め、「必要な根拠・写真・検証記録が揃い、参照先を記入しました。」にチェックして「下書き準備完了」にします。

「制作指示を保存」で `.md` を保存できます。これは制作を依頼するための資料です。「対応完了」は人が選ぶ作業管理上の状態であり、自動公開されたという意味ではありません。

## 7. タイトル・H1・説明文の修正案を作る

この操作は、実データの実績ページが「下書き準備完了」になったときに使えます。

1. 「下書き作成に進む」を押します。
2. 運用担当者が用意した「対象ページの公開用JSON」を選びます。
3. 「公開ページを取得」を押します。
4. 公開ページとJSONのタイトル・H1・説明文を照合します。違いがあれば、古いJSONでないか運用担当者に確認します。
5. タイトル案・H1案・説明文案を入力します。変えない項目は元の文章のままで構いません。
6. 「作成指示」を読み、対象クエリや目的が合っているか確認します。
7. 最初は「入力した修正案を下書きにする」を選びます。
8. 公開用情報であり、顧客の機密情報を含まないことを確認してチェックします。
9. 「修正案の下書きを作成」を押します。
10. 保存されたら「保存した下書きを開いて確認する」へ進みます。

元JSONはアプリ指定の実績データ形式で、800KB以下・作業と同じURLのものが必要です。HTMLやTSXを名前だけ `.json` に変えても使えません。公開HTMLを取得するだけでは元JSONは作れません。元JSONがない場合は、制作指示の保存まで進めて運用担当者へ渡してください。

公開ページの取得から30分を過ぎた場合は、再取得してから作成します。修正案が元とまったく同じ場合は、下書きは作られません。

「設定済みの外部AIで文章案を作る」は、運用担当者が接続した場合だけ使えます。選ぶと現在の生成文章と作成指示を外部APIに送ります。写真の説明など、文章に含まれる情報も対象です。手入力の修正案作成は、この外部AIを呼びません。

## 8. 技術確認をする（技術確認担当者）

依頼者は下書きの作業IDと画面のURLを担当者へ共有します。担当者は、運用担当者が技術確認用に設定した環境で同じ下書きを開きます。

1. 「保存したSEO下書きを開く」から対象を選びます。
2. 対象URLと変更前後の文章を確認します。
3. 「公開ページを再取得して確認」を押します。
4. 原本と一致したら、技術確認項目を自社検証の記録と照合します。
5. 項目ごとに「根拠を確認済み」または「要修正・確認待ちに戻す」を選びます。
6. 根拠または修正理由を記入し、「確認結果を記録」を押します。
7. すべての項目を確認します。

根拠メモには「検証記録のどこを見て、何を確認したか」を書きます。「確認しました」だけで終わらせず、後から判断をたどれる内容にしてください。

原本確認は30分間有効です。期限切れなら再取得します。公開HTMLの変更を検知した場合は、その下書きで確認を続けられません。依頼者が最新の原本とJSONを照合し、新しい下書きを作ります。

文章自体の修正も、新しい下書きで行います。この確認画面は文章を編集する画面ではありません。

## 9. 確認済みデータを引き渡す（依頼者）

1. 依頼者の環境で対象の下書きを開きます。
2. 確認待ちが0件であることと、確認履歴を読みます。
3. 公開原本の確認期限が切れていたら「公開ページを再取得して確認」を押します。
4. 「確認済みの引き渡しデータを保存」を押します。
5. 保存された `ページ名-seo-handoff.json` と作業IDを、運用担当者へ渡します。

| 保存ボタン | ファイルの用途 |
| --- | --- |
| 制作指示を保存 | 調査・根拠・準備内容をまとめたMarkdown |
| 修正案JSONを保存 | 修正後の文章を含む下書き。技術確認が完了する前でも保存できる |
| 確認済みの引き渡しデータを保存 | 元JSON・修正案・確認根拠をまとめた、運用担当者への引き渡し資料 |
| バックアップを保存 | ブラウザー内の台帳・検索比較・作業メモの復元用データ |

引き渡し後、本番データとの照合・差分レビュー・公開判断を行います。ダウンロードだけでは本番サイトは更新されません。

## 10. 保存と毎週の運用

台帳・検索比較・作業メモは、使っているブラウザーに保存されます。別の端末やブラウザーには自動で移りません。ブラウザーのデータを消す前、CSVを入れ替える前、デモを使う前にはバックアップを保存してください。

下書き・公開HTML・技術確認履歴はサーバー保存です。**画面の「バックアップを保存」だけでは、このサーバー側データは保存できません。** 運用担当者が別途バックアップします。

毎週の作業は次の順序が目安です。

1. 前回のバックアップを保存する。
2. 比較する検索データを取り込み、台帳を整える。
3. 依頼につながる候補を1〜2件選ぶ。
4. 既存作業の調査・検証・確認を進める。
5. 終了時に再度バックアップする。

更新直後はアプリが「経過観察」とする場合があります。通常のSEO改善は変化を確認しながら進め、誤記や機能不具合は待たずに運用担当者へ連絡します。

## 11. 困ったとき

| 状況 | 確認すること・次の操作 |
| --- | --- |
| CSVを取り込めない | ページ別CSVか、同日数・重ならない期間か、検索条件が同じかを確認。ZIPは展開する |
| 改善候補が出ない | データ量、重要度、更新日を確認。候補がないだけで問題がないとは判断しない |
| 今週の作業に追加できない | 週2件の上限、同じURLの未完了作業を確認 |
| 下書き作成ボタンがない | デモではないか、実績ページか、「下書き準備完了」かを確認 |
| JSONが読み込めない | 対応形式・800KB以下・対象URLとの一致を運用担当者に確認 |
| 公開ページを取得できない | TS配下の正式URL・末尾の `/` を確認。通信失敗なら再試行 |
| 技術確認を記録できない | 依頼者と別の担当者か、原本確認が30分以内かを確認 |
| 「公開ページが変更されています」 | 元JSONと公開ページを見直し、新しい下書きを作る |
| 「確認記録が更新されています」 | 再読み込みし、最新の差分と記録を確認してから操作する |
| 引き渡しボタンが使えない | 依頼者で開いているか、確認待ち0件か、原本確認が有効かを確認 |
| 別PCで作業が見えない | 台帳はバックアップから復元。下書きは同じサーバーか確認 |

## 付録：運用担当者の初期設定

一般の利用者は、運用担当者が案内したURLから使えます。以下はローカル検証用の手順です。

### 起動

Node.js 22以上を用意し、このリポジトリのフォルダーで実行します。

```sh
npm ci
npm run dev
```

`http://localhost:3000` を開きます。SEO画面は `/seo`、保存済み下書きは `/seo/drafts` です。既定の依頼者IDは `dev-requester` です。

### 技術確認担当者に切り替える（Windows PowerShell）

起動中のサーバーを `Ctrl+C` で止め、同じフォルダーで実行します。保存先は依頼者のときと同じものを使います。

```powershell
$env:SITEBOT_DEV_USER_ID = "reviewer-01"
$env:SITEBOT_DEV_USER_NAME = "技術確認担当"
$env:SITEBOT_DEV_USER_ROLE = "technical-reviewer"
npm run dev
```

これは開発用の役割切り替えです。実際の技術確認は別の担当者が行ってください。ログイン・本人認証を提供する設定ではありません。

既定の依頼者に戻す場合はサーバーを止め、以下を実行します。依頼者IDを独自に設定していた場合は、その元のIDに戻してください。

```powershell
Remove-Item Env:SITEBOT_DEV_USER_ID -ErrorAction SilentlyContinue
Remove-Item Env:SITEBOT_DEV_USER_NAME -ErrorAction SilentlyContinue
Remove-Item Env:SITEBOT_DEV_USER_ROLE -ErrorAction SilentlyContinue
npm run dev
```

### 動作を自動で確かめる

```sh
npm run verify:seo-sandbox
```

一時フォルダーで下書き・技術確認・引き渡し・照合・コピーへの適用を検証します。AIキーや本番データは不要です。画面を操作するコマンドではなく、成功・失敗をターミナルに表示する検証です。

### 引き渡しファイルを対象JSONと照合する

このリポジトリのフォルダーで、ファイルと対象リポジトリのパスを指定します。

```sh
node --import tsx src/cli.ts verify-seo-handoff --file "引き渡しファイルのパス" --root "対象リポジトリのパス"
```

対象は `content/achievements/ページ名.json` の対応形式です。結果の `ok: true` は照合成功を表します。ファイルは変更しません。CLIは最新の公開HTMLや、保存後に取り消された技術確認を照会しないため、適用前には最新状態を再確認してください。

TSXなど別形式の本番ソースへの接続は未実装です。照合成功だけで公開せず、本番の差分確認と公開承認を行います。

技術的な仕様や保存先の詳細は [SEO運用仕様](seo-workflow.md)、全体の起動設定は [README](../README.md) を参照してください。
