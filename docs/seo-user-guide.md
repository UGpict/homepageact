# SEO改善アプリ 利用ガイド

**まず操作したい方は [短い使い方](seo-quickstart.md) から始めてください。** この文書は、分からないことが出たときに読む詳しい説明です。

対象：ページの改善を依頼する人、技術内容を確認する人、運用担当者  
更新日：2026年10月11日  
対応版：PR #10・#11の機能を含む版

## このアプリで何をするの？

会社のホームページを見た人に、「この会社に相談してみよう」と思ってもらうためのアプリです。

たとえば、ページの説明が分かりにくいと、検索で見つけてもらっても相談につながりません。このアプリでは、検索の記録を見て直すページを選び、文章の修正案を作り、別の担当者に内容を確認してもらいます。

**基本の流れは「調べる → 直す案を作る → 別の人が確認する → 公開する担当者へ渡す」です。**

現在、アプリでできるのは担当者への引き渡しまでです。保存ボタンを押しただけで、誰でも見られる会社のホームページが変わることはありません。

### どこから読めばいい？

- 初めて触る人：まず「1. 言葉の説明」と「3. 最初の練習」を読む。
- 修正案を作る人：「4〜7」を順番に進め、確認が終わったら「9」へ進む。
- 技術内容を確認する人：「8」を読む。
- エラーなどで困った人：「11」を読む。
- アプリを起動・設定する人：最後の付録を読む。

このガイドはトップ画面の「検索データから改善を考える」の説明です。「実績を追加する」は、新しい紹介ページを作る別の機能です。

## 1. まず、この言葉だけ分かれば大丈夫

全部覚える必要はありません。分からない言葉が出たら、この表に戻ってください。

| 画面や説明書に出る言葉 | 意味 |
| --- | --- |
| SEO（エスイーオー） | 検索する人に、必要なページを見つけてもらいやすくするための改善 |
| Search Console（サーチコンソール） | 自分のサイトがGoogle検索でどれくらい表示・クリックされたかを確認するGoogleの道具 |
| URL（ユーアールエル） | ページの住所。`https://` などで始まる文字列 |
| ブラウザー | ホームページを見るアプリ。ChromeやEdgeなど |
| クエリ | 検索するときに入力した言葉。このガイドでは「検索語」とも呼ぶ |
| クリック数 | 検索結果からページがクリックされた回数 |
| 表示回数 | 検索結果にページが表示された回数 |
| CTR（シーティーアール） | 表示されたうち、何％がクリックされたか。100回表示・5回クリックなら5％ |
| 掲載順位・平均順位 | 検索結果のどの位置に出たかを集計した数字。数字が小さいほど上の位置。検索語や条件で変わるので、いつも同じ順位とは限らない |
| ページ台帳 | 管理するページの一覧表。ページごとの名前・目的・重要度を記録する |
| CSV（シーエスブイ） | 表のデータを保存するファイル。ここでは検索の記録をアプリに渡すために使う |
| JSON（ジェイソン） | 文章などを決まった項目に分けて保存するファイル。ここでは元ページや修正案のデータを入れる |
| Markdown・.md | 見出しや箇条書きを書ける文章ファイル。このガイドも `.md`。メモ帳でも読める |
| タイトル | ページの名前。検索結果などに使う |
| H1（エイチワン） | ページを開いたときの主見出し |
| 説明文 | 検索結果に出したい短い紹介文。検索側が別の文章を表示することもある |
| 自社検証 | 自分たちの会社で実験・観察して確かめること |
| 根拠 | 「そう言える理由」を確かめられる資料。実験記録や写真など |
| 下書き | 公開する前の文章案 |
| 原本 | 修正案を作るときの比較用に保存した、元のページの記録 |
| バックアップ・復元 | データの予備を保存すること・その予備から元に戻すこと |
| 本番サイト | お客様が実際に見ている会社のホームページ |

## 2. 誰が何をするか

| 担当 | 作業 |
| --- | --- |
| 依頼者 | 改善候補を選ぶ、調査・資料を用意する、修正案を作る、確認後のデータを保存する |
| 技術確認担当者 | 自分たちの実験記録と文章を見比べ、内容が正しいかと、その理由を記録する |
| 運用担当者 | アプリを使える状態にする、元のページのJSONを用意する、予備を保存する、公開サイトを更新する |

学校のレポートでいえば、依頼者が書き手、技術確認担当者が内容を確かめる読み手です。自分の思い込みを見落とさないように、別の人が確認します。

依頼者は自分の下書きの技術確認を記録できません。技術確認が終わっても、公開の判断は別途必要です。

現在は開発・検証用のアプリです。通常のログイン画面はなく、利用者と役割の設定は運用担当者が行います。利用者は運用担当者から案内されたURLを開いてください。

画面は上部の「1. データを用意」「2. ページを選ぶ」「3. 作業を進める」「ページ一覧・設定」で切り替えます。データの取り込み後は候補画面へ、作業追加後は作業画面へ進みます。途中でも「途中まで保存」で保存できます。

## 3. 最初の練習

**目的：本当の検索データを用意する前に、画面の使い方を知る。**

「架空データ」は練習用の数字です。会社の実績ではありません。誰かがすでに使っているPCなら、練習に切り替えてよいか運用担当者に確認してください。

1. トップ画面で「検索データから改善を考える」を開きます。
2. 既存データがある場合は、先に「データの保存・復元」を開き、「バックアップを保存」を押します。
3. 「架空データで試す」を押します。デモとは練習用の画面です。切り替えると、今のページ一覧や作業メモが練習用の内容に置き換わります。
4. 改善候補を読み、1件を「今週の作業に追加」します。
5. 「調査・準備を記入」を開き、項目と作業状態を確認します。
6. 練習が終わったら「デモを終了する」を押します。元のデータを戻す場合は、保存したバックアップを復元します。

デモで試せるのは、候補選びや準備内容の記入などです。実ページの下書き作成は実データの作業で行います。比較データが既にあると、デモ開始ボタンが使えない場合があります。デモのために実データを消す必要はありません。

## 4. 検索データを取り込む

**目的：以前と最近の数字を比べ、見てもらう機会が減ったページなどを探す。**

ここでの「取り込む」は、用意したファイルをアプリに読み込ませることです。Search Consoleを使ったことがなければ、自分でファイルを作らず、運用担当者に用意してもらってください。

### 用意するもの

- 前期間と今回の期間、それぞれの「ページ別CSV」
- それぞれの開始日・終了日
- 検索条件のメモ

CSVはSearch Consoleから用意します。運用担当者に依頼するときは、次のように伝えてください。

> 受託分析部門のサイト（https://www.macsystems.co.jp/ts/ で始まるページ）を対象に、以前と最近を比較したいです。日数が同じで、日付が重ならない2期間の「ページ別CSV」をください。クリック数・表示回数・掲載順位が必要です。期間の日付と、国・端末などの検索条件も教えてください。

たとえば「2026年8月1日〜28日」と「2026年8月29日〜9月25日」は、重ならない28日間です。これは入力例なので、実際に出力したCSVの期間に置き換えます。

「同じ検索条件」とは、たとえば両方とも日本からの検索だけ、両方ともスマートフォンだけ、というように、集計する範囲をそろえることです。片方だけ範囲が違うと、公平に比較できません。

### 画面での操作

1. 「1. 検索データを取り込む」で、前期間の日付とCSVを選びます。
2. 今回の期間の日付とCSVを選びます。
3. 「検索条件のメモ」を入力します。例：`ウェブ / 国・デバイス指定なし / ページURLは https://www.macsystems.co.jp/ts/ で始まるもの`。
4. 両方が同じ条件で集計され、まだ集計途中の数字ではないことを確認し、チェックを付けます。分からなければ、CSVを用意した人に聞きます。
5. 「取り込んで比較する」を押します。

`.zip` は複数のファイルをひとまとめにしたものです。Windowsなら右クリックして「すべて展開」を選び、中にあるページ別のCSVを選びます。1行が1ページになっているファイルが必要です。検索語ごと・日付ごとの表や、2期間の比較結果を一つにしたCSVは使えません。日付はファイルから自動判定できないため、正確に入力してください。

取り込みが終わると、ページごとの比較結果と改善候補を確認できます。ここでは、まだ文章は変わりません。

## 5. 改善するページを選ぶ

**目的：相談につながりそうなページから、今週やることを絞る。**

先に上部の「ページ一覧・設定」を選び、「4. ページ台帳」で、管理するための名前、増やしたい相談、重要度、最後に内容を変えた日を入力します。更新日が不明なら空欄で構いません。台帳の編集だけで公開サイトの文章が変わることはありません。

重要度は次を目安に設定します。

| 重要度 | 判断の目安 |
| --- | --- |
| 3 | 「頼めるか」「いくらかかるか」という相談につながる |
| 2 | どの会社に頼むかを選ぶ材料になる |
| 1 | 技術や試験方法を理解する助けになる |
| 0 | 今は、このページから新しいお客様を集める予定がない |

「2. 改善候補を確認する」で理由を読み、進めるページの「今週の作業に追加」を押します。選べるのは日本時間の月曜始まりで週2件までです。同じページの未完了作業は重複して追加できません。

たとえば「表示される回数は同じなのに、クリックが減った」という結果なら、ページ名が分かりにくくないか調べるきっかけになります。ただし、この数字だけで原因は決まりません。

**候補に出た理由だけで書き換えないでください。** ページ全体の平均順位から、特定の検索語の順位は分かりません。対象URLの検索語と実際のページを確認してから、変える箇所を決めます。「データ不足」は不要なページという意味ではありません。

## 6. 調査・実験・写真を準備する

**目的：「何を変えるか」と「なぜそう書けるか」を、別の人にも伝わるようにする。**

「3. 選んだ作業を進める」から「調査・準備を記入」を開きます。

| 入力欄 | 書く内容の例・目安 |
| --- | --- |
| この改善で増やしたい相談 | 材料や試料のどの困りごとについて相談してほしいか |
| 確認した検索語（クエリ） | 実際にデータで確認した検索語 |
| 検索語を調べた場所・日付 | 対象URL、調査期間、確認日 |
| 調査結果・変更したい箇所 | 現在不足している説明と、必ず残す写真・表・注意書き |
| 追加の自社検証計画 | 試料・条件・比較方法。不要ならその理由 |
| 写真・図の準備 | 写真の保存場所、写っているものの大きさが分かる目盛り、撮影条件。不要ならその理由 |
| 説明が正しいと分かる資料 | 自社の実験記録の番号、観察した内容、写真の名前や番号など |
| 確認できたこと・まだ分からないこと | 今回の条件で言えること、未確認のこと |

ここには、顧客名・案件原文・顧客の写真・機密情報を入力しません。お客様から預かった情報は、勝手に公開できないためです。公開する説明は、自分たちで実験・観察して確かめた内容から用意します。入力例の数値や他ページの結果を、自分の実験結果として流用しないでください。

記入の考え方の例：実験がある条件でしか成功していないなら、「どんな条件でもできる」とは書きません。「今回確かめた条件ではできた。別の条件はまだ確認していない」と書きます。

準備画面では3つの質問に答えます。分からない項目は「分からないので後で確認する」で飛ばせます。「途中まで保存」を押すと「調査中」になります。

「担当者への相談メモを保存」は、記入済みの内容と未確認の項目を文章ファイルにまとめます。制作指示とは別の、準備途中の相談用です。確認が必要な項目は最後の質問に一覧で表示します。

| 作業の状態 | どんなときに選ぶか |
| --- | --- |
| 今週の作業 | やることとして選んだところ |
| 調査中 | 検索語や今のページを調べている |
| 検証・写真待ち | 実験や写真など、必要な材料がまだそろっていない |
| 下書き準備完了 | 修正案を作るための調査・資料がそろった |
| 対応完了 | 決めた作業が終わったことを、人が確認した |
| 見送り | 今回は進めないと決めた |

最後の質問で必要項目を埋め、「必要な資料・写真がそろい、保存場所も確認しました。」にチェックし、「準備を完了して保存」を押すと「下書き準備完了」になります。途中で進めないと決めた場合は「作業を終了・見送りにする」を開いて「今回は見送る」を選べます。

「制作指示を保存」で `.md` を保存できます。これは制作を依頼するための資料です。「対応完了にする」は準備項目がそろったときに選べる作業管理上の操作であり、自動公開されたという意味ではありません。

## 7. タイトル・H1・説明文の修正案を作る

**目的：元のページと比べながら、3種類の文章の修正案を保存する。**

「元JSON」は、元の文章や写真の情報をアプリ用の形でまとめたファイルです。運用担当者に「このページを直したいので、アプリで使える元JSONをください」と、対象ページのURLを添えて依頼します。自分でプログラムを書く必要はありません。

この機能が変えるのは、ページ名・主見出し・短い説明文です。本文を全部書き直したり、新しい写真を追加したりする操作は含みません。

この操作は、実データの実績ページが「下書き準備完了」になったときに使えます。

1. 「下書き作成に進む」を押します。
2. 運用担当者が用意した「対象ページの公開用JSON」を選びます。
3. 「公開ページを取得」を押します。
4. 公開ページとJSONのタイトル・H1・説明文を見比べます。違いがあれば、古いJSONでないか運用担当者に確認します。
5. タイトル案・H1案・説明文案を入力します。変えない項目は元の文章のままで構いません。
6. 必要なら「文章の作り方を変える（任意）」を開き、作成指示を確認します。
7. 最初は「入力した修正案を下書きにする」を選びます。
8. 公開用情報であり、顧客の機密情報を含まないことを確認してチェックします。
9. 「修正案の下書きを作成」を押します。
10. 保存されたら「保存した下書きを開いて確認する」へ進みます。

ファイルはアプリ指定の形式で、800KB以下・作業と同じページのものが必要です。KBはファイルの大きさの単位です。ホームページを保存したファイルなどを、名前だけ `.json` に変えても使えません。「公開ページを取得」は比較用の記録を保存する操作なので、それだけでは元JSONの代わりになりません。元JSONがない場合は、制作指示の保存まで進めて運用担当者へ渡してください。

公開ページの取得から30分を過ぎた場合は、再取得してから作成します。修正案が元とまったく同じ場合は、下書きは作られません。

「設定済みの外部AIで文章案を作る」は、運用担当者が接続した場合だけ使えます。選ぶと現在の生成文章と作成指示を接続先のAIサービスに送ります。写真の説明など、文章に含まれる情報も対象です。手入力の修正案作成は、この外部AIを呼びません。

## 8. 技術確認をする（技術確認担当者）

**目的：読みやすさだけでなく、書いた内容が実験の結果と合っているかを確かめる。**

作業IDは、下書きを見分けるための番号です。画面に表示される `job-` で始まる文字列を使います。

依頼者は下書きの作業IDと画面のURLを担当者へ共有します。担当者は、運用担当者が技術確認用に設定した環境で同じ下書きを開きます。

1. 「保存したSEO下書きを開く」から対象を選びます。
2. 対象URLと変更前後の文章を確認します。
3. 「公開ページを再取得して確認」を押します。
4. 「原本HTMLと一致しています」と表示されたら、確認する項目を自社の実験記録と見比べます。HTMLはページの文字や構造を記したデータです。ここでは詳しい仕組みを覚える必要はありません。
5. 項目ごとに「根拠を確認済み」または「要修正・確認待ちに戻す」を選びます。
6. 根拠または修正理由を記入し、「確認結果を記録」を押します。
7. すべての項目を確認します。

根拠メモには「検証記録のどこを見て、何を確認したか」を書きます。「確認しました」だけで終わらせず、後から判断をたどれる内容にしてください。

たとえば根拠メモは「自社検証の記録［番号］と写真［名前］を見て、本文の説明と一致することを確認。確認できた範囲は［条件］まで」のように書きます。角かっこの中は、実際の記録に置き換えてください。

原本確認は、修正案を作っている間に元のページが変わっていないかを調べる操作です。確認結果は30分間有効です。期限切れなら再取得します。公開HTMLの変更を検知した場合は、その下書きで確認を続けられません。依頼者が最新の元ページとJSONを見比べ、新しい下書きを作ります。

文章自体の修正も、新しい下書きで行います。この確認画面は文章を編集する画面ではありません。

## 9. 確認済みデータを引き渡す（依頼者）

**目的：確認が終わった修正案を、サイトを更新する担当者へ渡す。**

1. 依頼者の環境で対象の下書きを開きます。
2. 確認待ちが0件であることと、確認履歴を読みます。
3. 公開原本の確認期限が切れていたら「公開ページを再取得して確認」を押します。
4. 「確認済みの引き渡しデータを保存」を押します。
5. 保存された `ページ名-seo-handoff.json` と作業IDを、運用担当者へ渡します。

| 保存ボタン | ファイルの用途 |
| --- | --- |
| 制作指示を保存 | 調査・根拠・準備内容をまとめたMarkdown |
| 修正案JSONを保存 | 修正後の文章を含む下書き。技術確認が完了する前でも保存できる |
| 確認済みの引き渡しデータを保存 | 元JSON・修正案・確認根拠をまとめた、運用担当者への引き渡し資料 |
| バックアップを保存 | ブラウザー内の台帳・検索比較・作業メモの復元用データ |

引き渡し後、運用担当者が、実際のサイトの元データと見比べ、変わる箇所を確認してから、公開してよいかを判断します。ダウンロードだけでは本番サイトは更新されません。

## 10. 保存と毎週の運用

台帳・検索比較・作業メモは、使っているブラウザーに保存されます。別の端末やブラウザーには自動で移りません。ブラウザーのデータを消す前、CSVを入れ替える前、デモを使う前にはバックアップを保存してください。

下書き・取得した公開ページ・技術確認の履歴は、アプリを動かしているコンピューター（サーバー）に保存されます。**画面の「バックアップを保存」だけでは、このサーバー側データは保存できません。** 運用担当者が別途バックアップします。

毎週の作業は次の順序が目安です。

1. 前回のバックアップを保存する。
2. 比較する検索データを取り込み、台帳を整える。
3. 依頼につながる候補を1〜2件選ぶ。
4. 既存作業の調査・検証・確認を進める。
5. 終了時に再度バックアップする。

更新直後はアプリが「経過観察」とする場合があります。通常のSEO改善は変化を確認しながら進め、誤記や機能不具合は待たずに運用担当者へ連絡します。

## 11. 困ったとき

意味の分からないエラーが出たら、同じ操作を繰り返す前に、表示された文章と「何をしていたか」を運用担当者に伝えてください。下書きの画面なら作業IDも添えると探しやすくなります。

| 状況 | 確認すること・次の操作 |
| --- | --- |
| CSVを取り込めない | ページ別CSVか、同日数・重ならない期間か、検索条件が同じかを確認。ZIPは展開する |
| 改善候補が出ない | データ量、重要度、更新日を確認。候補がないだけで問題がないとは判断しない |
| 今週の作業に追加できない | 週2件の上限、同じURLの未完了作業を確認 |
| 下書き作成ボタンがない | デモではないか、実績ページか、「下書き準備完了」かを確認 |
| JSONが読み込めない | 対応形式・800KB以下・対象URLとの一致を運用担当者に確認 |
| 公開ページを取得できない | `https://www.macsystems.co.jp/ts/` で始まり、最後が `/` のURLか確認。通信失敗なら再試行 |
| 技術確認を記録できない | 依頼者と別の担当者か、原本確認が30分以内かを確認 |
| 「公開ページが変更されています」 | 元JSONと公開ページを見直し、新しい下書きを作る |
| 「確認記録が更新されています」 | 再読み込みし、どの文章が変わるかと最新の記録を確認してから操作する |
| 引き渡しボタンが使えない | 依頼者で開いているか、確認待ち0件か、原本確認が有効かを確認 |
| 別PCで作業が見えない | 台帳はバックアップから復元。下書きは同じサーバーか確認 |

## 付録：アプリを起動する人向け

ここからは、アプリを自分のPCで動かす担当者のための説明です。画面を操作するだけの人は読む必要がありません。

| 言葉 | 意味 |
| --- | --- |
| リポジトリ | アプリのプログラムや説明書をまとめて管理している場所。ここではダウンロードした `homepageact` のフォルダー |
| Node.js | このアプリをPCで動かすためのソフト |
| コマンド | PCに処理を頼むための文字列。下の枠の中の行がこれに当たる |
| PowerShell・ターミナル | コマンドを入力するための画面 |
| サンドボックス | 本当のデータに影響を与えず、動作を試すために分けた場所 |
| パス | PCの中でファイルやフォルダーがどこにあるかを表す住所 |
| CLI | ボタンの代わりに、コマンドを入力して使う仕組み |


一般の利用者は、運用担当者が案内したURLから使えます。以下はローカル検証用の手順です。

### 起動

1. Node.js 22以上がPCに入っていることを確認します。入れ方が分からない場合は、PCの管理担当者に依頼してください。
2. ダウンロードした `homepageact` フォルダーを開きます。
3. Windowsならそのフォルダーで右クリックし、「ターミナルで開く」を選びます。`package.json` というファイルがあるフォルダーで実行してください。
4. 次のコマンドを1行ずつ入力し、Enterを押します。最初の行が終わってから次の行を実行します。

```sh
npm ci
npm run dev
```

`npm ci` は必要なソフトの部品をそろえる操作、`npm run dev` はアプリを起動する操作です。起動したターミナルは開いたままにします。

ブラウザーのアドレス欄に `http://localhost:3000` を入力して開きます。`localhost` は「今使っている自分のPC」という意味です。

検索の画面は `http://localhost:3000/seo`、保存済み下書きは `http://localhost:3000/seo/drafts` です。特に設定しなければ、依頼者の識別名は `dev-requester` になります。

### 技術確認担当者に切り替える（Windows PowerShell）

起動したターミナルを選び、Ctrlキーを押しながらCキーを押してアプリを止めます。次の行は、アプリに「技術確認担当者として使う」と伝える設定です。同じフォルダーのPowerShellで、1行ずつ実行します。保存先は依頼者のときと同じものを使います。

```powershell
$env:SITEBOT_DEV_USER_ID = "reviewer-01"
$env:SITEBOT_DEV_USER_NAME = "技術確認担当"
$env:SITEBOT_DEV_USER_ROLE = "technical-reviewer"
npm run dev
```

これは開発用の役割切り替えです。実際の技術確認は別の担当者が行ってください。ログイン・本人認証を提供する設定ではありません。

最初の依頼者設定に戻す場合はアプリを止め、以下を実行します。依頼者IDを独自に設定していた場合は、その元のIDに戻してください。

```powershell
Remove-Item Env:SITEBOT_DEV_USER_ID -ErrorAction SilentlyContinue
Remove-Item Env:SITEBOT_DEV_USER_NAME -ErrorAction SilentlyContinue
Remove-Item Env:SITEBOT_DEV_USER_ROLE -ErrorAction SilentlyContinue
npm run dev
```

### 動作を自動で確かめる

```sh
npm run verify:seo-sandbox
```

テスト用のフォルダーとデータを自動で作り、下書きから確認・引き渡しまで試します。最後にテスト用データを削除します。外部AIの利用設定や実際の会社のデータは不要です。結果の `pass` は成功、`fail` は失敗したテストの数です。画面を操作するコマンドではなく、成功・失敗をターミナルに表示する検証です。

### 引き渡しファイルを対象JSONと見比べる

`homepageact` フォルダーで実行します。下の「引き渡しファイルのパス」は保存したJSONの場所、「対象リポジトリのパス」は更新対象のサイトのプログラムがあるフォルダーの場所に置き換えます。引用符 `"` は残してください。分からない場合は、サイトを作った担当者に確認します。

```sh
node --import tsx src/cli.ts verify-seo-handoff --file "引き渡しファイルのパス" --root "対象リポジトリのパス"
```

対象は `content/achievements/ページ名.json` の対応形式です。結果の `ok: true` は元のデータと一致し、修正案の形式などの確認にも通ったことを表します。ファイルは変更しません。このコマンドは、公開ページが今も同じか、確認担当者が後から判断を取り消していないかまでは調べません。実際に変更を反映する前に、画面と公開ページで最新の状態を確認してください。

実際のサイトが、ここで使うJSONと違う形式で作られている場合は、別の接続作業が必要です。たとえばTSXというプログラムファイルを直接更新する機能は、まだありません。照合が成功した後も、担当者が変更箇所を確認し、公開してよいかを判断します。

技術的な仕様や保存先の詳細は [SEO運用仕様](seo-workflow.md)、全体の起動設定は [README](../README.md) を参照してください。
