# sitebot

TS部署サイトの更新を、モデルの善意ではなくハーネスで拘束するための実験実装です。実績とコラムの新規作成に加え、データファイル化されたページの文章修正、確認後の1セクションだけの書き直し、公開前の画像処理までを扱います。ブラウザからは、実績ページの下書き作成とプレビュー、技術確認が必要な項目の表示までを行えます。ログイン、メール、本番反映、GitHubへのPR作成はまだありません。

## ハーネスが強制すること

- モデルが返せるのは `generated` の断片だけです。`facts`、`review`、`commitSha`、書き込み先パスが混ざったJSONは棄てます。
- 書き込み先はレシピの `output` テンプレートと、`^[a-z0-9-]+$` の slug からハーネスが決めます。
- 公開JSONに承認は書きません。承認は `.sitebot/approvals.json`（gitの外）に、commit SHA 単位で残します。HEADが先に進むと、その承認ではマージできません。
- 列挙、計算式、例示の断り書き、スケール、自社見解は、人間が入力した原文をテンプレートが出します。
- 会社名などの機密語は生成プロンプトに載せません。本文に出たら公開ファイルを書きません。
- 相談チャットの文字列は生成ペイロードにフィールドがありません。
- 出典の無い数値は `pending` の主張になり、技術確認が終わるまでマージできません。見本記事にある数値は出典になりません。
- 確認済み知識と文言が一致しても、自動では `ok` にしません。依頼者は技術確認者になれません。
- `claims.yaml`、`taxonomy.yaml`、`verified-claims.yaml` は通常レシピから書けません。他ファイルへの相互リンク（`also_may_edit`）は、操作の型が決まるまで拒否します。
- `text_edit` は、すでにデータファイルになっている実績ページだけを書き換える。slug と `facts` は変えられない。変更前後の差分に数値・規格・化学式・否定があれば L2 になり、技術確認が要る。分類できない差分も L2 です。
- 技術確認の書き直しは、指定した Point だけを差し替える。ほかの Point が変わっていたら失敗し、その Point の確認は `pending` に戻る。
- 画像はデコードして WebP に変換し、EXIF / IPTC / XMP を落とし、ファイル名は内容のハッシュにする。元のファイル名は公開名に残さない。

## 画面

非エンジニア向けの入口は、自由な指示欄ではなく「実績を追加する」です。入力はフォームに限り、文章生成とファイル保存は既存のハーネスを通ります。APIキーが無いときは、入力内容から決まる下書き（mock）を使います。

```bash
npm install
npm run dev
```

ブラウザで http://localhost:3000 を開きます。下書きと画像は `data/sitebot` に保存され、リポジトリには入りません。保存先を画面から指定することはできません。

任意の環境変数:

- `SITEBOT_PROVIDER` — 未設定または `mock`。`http` にすると外部の生成APIを呼びます。
- `SITEBOT_GENERATION_URL` — `SITEBOT_PROVIDER=http` のとき必須。
- `SITEBOT_GENERATION_API_KEY` — 生成APIへ Bearer で渡します。ファイルには書きません。
- `SITEBOT_CONFIDENTIAL_TERMS` — カンマまたは改行区切り。本文に含まれると下書きを作りません。
- `SITEBOT_DEV_USER_ID` / `SITEBOT_DEV_USER_NAME` — 開発用の依頼者。未設定時は `dev-requester` / `開発用ユーザー`。
- `SITEBOT_DEV_USER_ROLE` — `technical-reviewer` のときだけ開発用技術確認担当者。その他・未設定は依頼者。認証の代用にはならず、依頼者と異なるIDが必要。
- `SITEBOT_PACK_ROOT` / `SITEBOT_DATA_ROOT` — サイト定義と下書きの保存先。通常は変更しません。

## コマンド

```bash
npm test
npm run typecheck
npm run build:web
npm run sitebot -- run-fixture bga --root out
npm run sitebot -- prepare-image --file photo.jpg --kind achievement --root out
```

`run-fixture bga` は、公開中のBGA実績ページをスキーマに写したフィクスチャをハーネスに通します。プレビューは `out/preview/bga.txt` です。電話番号や住所はコンテンツに含めず、共通レイアウト側に残します。きっかけの文面は `origin` のフィールドから組み立てるため、公開ページの敬称とは一致しません。title と h1 は分けたままです。

## SEOレビュー

トップの「検索データから改善を考える」（`/seo`）から、ページ台帳、Search Consoleのページ別CSVの2期間比較、根拠付き改善候補を利用できます。CSVと台帳はブラウザ内に保存し、外部AIへ送信しません。「架空データで試す」で入力なしでも確認できます。

改善候補を今週の作業に追加して、調査・追加検証・写真・根拠を記録し、下書き準備が揃ったら制作指示をMarkdownで保存できます。旧版の保存データは移行して読み込めます。実績ページでは、公開用の構造化JSONからタイトル・H1・説明文の下書きを既存ハーネス経由で作成し、差分と修正案JSONを確認できます。外部AIは設定済みAPIを明示的に選択した場合だけ使用します。

保存した下書きは `/seo/drafts` から開き直せます。依頼者と別の技術確認担当者は確認根拠と「確認済み／要修正」を記録できます。確認履歴はサーバー保存で、公開承認にはなりません。GSC API連携、定期実行、本番データ同期、認証、PR・公開は今後接続します。データの準備、候補の判定条件と保存上の注意は [SEO運用手順](docs/seo-workflow.md) を参照してください。

`/seo/sources` ではTSサイトの公開HTMLを取得・保存し、タイトル・H1・説明文・canonical・見出し・画像一覧を読み取れます。実績ページの下書き入力画面からも取得し、JSONのSEO文章と照合できます。HTMLから根拠データや構造化JSONを推測して作ることはありません。

新しい下書きには、取得から30分以内の公開HTMLを原本として紐付けます。確認画面で公開ページを再取得し、HTML全体が一致した確認から30分以内だけ技術確認を記録できます。変更を検知した下書きは過去の確認を有効扱いせず、元データを見直して作り直します。従来の原本未紐付けの下書きは閲覧・ダウンロードできますが、技術確認は進められません。
